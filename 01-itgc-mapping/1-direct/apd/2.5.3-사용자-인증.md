# 2.5.3 사용자 인증

> **기준 판본**: [KISA ISMS-P 인증기준 안내서(2023.11.23)](https://www.isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do).
> **관련 법령**: 2026-07-26 기준.
> **내용 구분**: §1은 KISA 안내서와 법령을 요약했다. §3~§4에는 작성자의 실무 경험을 반영했다.

## 1. ISMS-P 기준 요약

### 인증기준
사용자가 정보시스템과 개인정보 및 중요정보에 접근할 때는 **안전한 인증절차**를 적용하고 필요에 따라 **강화된 인증방식**도 적용해야 한다. 또한 **로그인 횟수 제한, 불법 로그인 시도 경고** 등 비인가자 접근 통제방안을 수립·이행하여야 한다.

### 주요 확인사항 (KISA 안내서)
1. 정보시스템 및 개인정보처리시스템에 대한 접근은 사용자 인증, 로그인 횟수 제한, 불법 로그인 시도 경고 등 안전한 사용자 인증 절차에 따라 통제하고 있는가?
2. 정보통신망을 통하여 외부에서 개인정보처리시스템에 접속하려는 경우에는 법적 요구사항에 따라 **안전한 인증수단 또는 안전한 접속수단**을 적용하고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무)
- 개인정보의 안전성 확보조치 기준 제5조 (접근권한 관리), 제6조 (접근통제)

### 인증 수단 분류 (KISA 안내서)

| 구분 | 인증 수단 | 비고 |
|---|---|---|
| 지식 기반 | 비밀번호 | 작성규칙·변경주기와 기본 계정 차단 |
| 소유 기반 | 인증서(PKI), OTP | 개인키 안전 보관 / OTP 토큰·모바일 OTP |
| 생체 기반 | 지문·홍채·얼굴 | FIDO. 생체정보 안전 관리 |
| 기타 (보완) | IP·MAC·기기 일련번호·위치 | 단독 인증수단이 아닌 보완통제로 적용 |

### 계정 도용·불법 인증 통제 (KISA 안내서 + 법령 1차)

**1. 인증 실패횟수 제한** — 안전성 확보조치 기준 제5조제6항
- [현행 제5조제6항](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&chrClsCd=010201&dashNo=&docCls=jo&joBrNo=00&joNo=0005&urlMode=admRulScJoRltInfoR)은 일정 횟수 이상 인증에 실패하면 개인정보처리시스템 접근을 제한하는 등 필요한 조치를 요구한다.
- **법령은 구체적인 횟수를 정하지 않는다.** 회사가 위험평가와 정책에 따라 정한다.
- 잠금 후 해제 절차(셀프서비스/관리자 승인)도 회사 정책

**2. 접속 유지시간 제한 (Session/Idle Timeout)** — 안전성 확보조치 기준 제6조제4항
- [현행 제6조제4항](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&chrClsCd=010201&dashNo=&docCls=jo&joBrNo=00&joNo=0006&urlMode=admRulScJoRltInfoR)은 개인정보취급자가 일정시간 이상 업무처리를 하지 않으면 자동 차단 등 필요한 조치를 하도록 요구한다.
- **법령은 구체적인 시간을 정하지 않는다.** 회사가 위험평가와 정책에 따라 정한다.
- KISA 안내서: "서버별 특성, 업무 환경, 위험의 크기, 법적 요구사항 등을 고려하여 세션 유지시간 설정"

**3. 동시 접속 제한** — KISA 안내서 (`동일 계정으로 동시 접속 시 접속차단 조치 **또는** 알림 기능 등`)
- KISA 안내서는 차단 또는 알림 기능 등을 예시로 든다. 적용 방식은 시스템 위험도와 회사 정책에 따라 결정한다.

**4. 불법 로그인 시도 경고** — KISA 안내서 예시
- **국외 IP 등 등록되지 않은 IP주소**에서의 접속 시 **차단 및 통지**
- **주말·야간 접속** 시 문자 알림
- **관리자 등 특수권한 로그인** 시 알림
- (위 외 유형도 회사 위험평가 결과에 따라 자율 추가 가능)

**5. IP 기반 접근 제한 + 유출 시도 탐지** — 안전성 확보조치 기준 제6조제1항
- 개인정보처리시스템 접속 권한을 IP주소 등으로 제한 (인가받지 않은 접근 차단)
- 접속한 IP주소 등을 분석해서 **개인정보 유출 시도 탐지 및 대응**
- 허용 IP 제한뿐 아니라 접속 IP 분석을 통한 유출 시도 탐지·대응도 요구하므로 보안관제 영역과 연결된다.

### 외부 접속 시 안전한 인증수단 (안전성 확보조치 기준 제6조제2항)

[현행 제6조제2항](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&chrClsCd=010201&dashNo=&docCls=jo&joBrNo=00&joNo=0006&urlMode=admRulScJoRltInfoR)은 외부 접속 시 인증서·보안토큰·일회용 비밀번호 등 안전한 인증수단을 적용하도록 한다. 이용자가 아닌 정보주체의 개인정보만 처리하는 시스템은 VPN 등 안전한 접속수단 또는 안전한 인증수단 중 하나를 적용할 수 있다.

| 대상 시스템 | 적용 필요 사항 |
|---|---|
| **이용자 개인정보 처리시스템** | 안전한 인증수단 **필수** (인증서·보안토큰·OTP) |
| 이용자 아닌 정보주체 처리시스템 | 안전한 접속수단(VPN 등) **또는** 안전한 인증수단 |

**핵심 갈림길**: "이용자(서비스 가입자·고객)" 개인정보를 처리하는 시스템이면 VPN만으로는 부족하고 법령상 **안전한 인증수단**이 필요하다. 이는 실무에서 MFA로 구현되는 경우가 많지만, 법령 문언이 모든 안전한 인증수단을 일률적으로 MFA라고 부르는 것은 아니다. "이용자 아닌 정보주체"(예: 임직원·거래처·외주인력 개인정보만 처리) 시스템이면 VPN 등 안전한 접속수단으로도 충족할 수 있다.

### 결함사례 (KISA 안내서)
- **사례 1**: 개인정보취급자가 공개된 외부 인터넷망을 통해 이용자 개인정보 처리시스템 접근 시 안전한 인증수단을 적용하지 않고 ID·비밀번호 방식으로만 인증
- **사례 2**: 로그인 실패 시 해당 ID 존재 여부·비밀번호 틀림을 자세히 표시 + 로그인 실패횟수 제한 없음

## 3. IT감사에서는 이렇게

ISMS-P의 전체 요구사항과 한국 비금융 ITGC에서 통상 검증하는 범위는 다르므로 아래와 같이 구분한다.

### 3-A. 한국 비금융 ITGC 실무 적용

비금융 회계감사 ITGC에서 2.5.3 영역은 보통 아래 3가지만 본다. 세 설정값이 한 화면에 함께 표시되므로 한 번의 시스템 설정 캡처로 동시에 검증할 수 있다.

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 1. 비밀번호 정책 | 시스템 설정값 캡처 (길이·복잡도·주기) | 전 시스템 | 시스템별 설정 확인 + 대표 1건 재수행 |
| 2. 로그인 실패횟수 제한 | 시스템 설정값 캡처 (n회 후 잠금) + 잠금 해제 절차 | 전 시스템 | 시스템별 설정 확인 + 대표 1건 재수행 |
| 3. 세션 타임아웃 | 시스템 설정값 캡처 (idle timeout 분) | 전 시스템 | 시스템별 설정 확인 + 대표 1건 재수행 |

**법적 의무 관련 별도 확인**(이용자 개인정보 처리시스템에 한정):

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 4. 외부 접속 인증수단 | 외부 접속 경로 목록과 인증서·보안토큰·OTP 적용 여부 검증(제6조제2항) | 이용자 개인정보 처리시스템의 외부 접속 경로 | 100% |

### 3-B. ISMS-P 추가 요구사항 중 일반 ITGC 범위 밖

아래 항목들은 KISA 안내서·법령에 명시되어 있어 ISMS-P 인증심사에서는 검증되지만, **회계감사 ITGC에서는 거의 보지 않거나 보안 영역으로 분리된다.** ISMS-P 인증을 별도로 받으려는 회사가 아니면 ITGC에서 다루지 않아도 무방하다.

| ISMS-P 요구사항 | 확인 절차 | 주된 담당 영역 |
|---|---|---|
| 동시 접속 제한 | 설정값 + 동시 접속 발생 시 차단 또는 알림 | ISMS-P 인증심사 |
| 로그인 실패 메시지 | ID 존재 여부와 비밀번호 오류를 구분해 노출하는지 검증 | ISMS-P 인증심사 |
| SSO 강화 인증 / 재인증 | SSO 시스템 + 중요 기능 접근 시 재인증 | ISMS-P 인증심사 (SSO 도입사 한정) |
| 인증 수단 분류 (지식·소유·생체) | 시스템별 인증수단 목록과 적용 사유 | ISMS-P 인증심사 |
| IP 기반 접근 제한 | 화이트리스트 IP 정책 + 설정 (제6조제1항) | **보안 영역** (방화벽·VPN) |
| 유출 시도 탐지·대응 | SIEM·UEBA 룰 + 대응 절차 (제6조제1항 후단) | **보안 영역** (SOC) |
| 불법 로그인 경고 | 국외 IP 차단·통지, 야간 알림, 특수권한 알림 등 | **보안 영역** (보안관제) |

**범위 차이**: ISMS-P는 정보보호 전반을 다루지만, 회계감사 ITGC는 재무제표 신뢰성과 관련된 통제를 중심으로 본다. 보안 통제는 보안 조직이나 별도 보안 진단에서 검증하는 경우가 많다.

## 4. Q&A

### Q1. 어느 시스템에 안전한 인증수단이 필요하고, 어느 시스템에 ID/PW만으로 충분한가?
A. **회사 위험평가 결과가 1순위이며, 법적 의무는 보조 점검 항목으로 확인한다.**
- **위험평가 기반 (1순위, ITGC 본질)**:
  - 회사가 시스템별 위험등급(상·중·하)을 분류하고 MFA 적용 정책을 수립했는지 확인
  - 일반 정보시스템(내부망 ERP·HR·DB) → ID·비밀번호와 비밀번호 정책으로 통상 충분
  - 관리자 계정·재무 결산·DB 직접접근 등 고위험 → MFA 권고
  - ITGC에서는 회사 정책과 일관된 적용 여부를 검증한다.
- **법적 의무 (보조 점검)**:
  - 외부 인터넷망에서 이용자 개인정보 처리시스템 접근 시 안전한 인증수단 적용 (안전성 확보조치 기준 제6조제2항)
  - 법령 위반으로 과징금·우발부채 등 재무 영향이 발생할 수 있으므로 필요하면 보조적으로 확인
- **결함 판단**:
  - 회사 위험평가·정책 자체가 부재 → 결함
  - 정책은 있으나 시스템 적용이 불일치함(정책은 MFA, 실제는 ID·비밀번호만 적용) → 결함
  - 법령상 안전한 인증수단이 필요한 시스템에 ID·비밀번호만 적용 → 법규 준수와 재무적 영향을 별도 평가

### Q2. 로그인 실패 횟수 제한 — 몇 회가 표준? KISA에 숫자 있나?
A. **KISA와 현행 고시는 구체적인 횟수를 정하지 않는다. 회사 정책과 위험평가가 기준이다.**
- **KISA 안내서**: "인증 실패횟수 제한"·"일정 횟수 이상 인증에 실패한 경우 접근 제한" (안전성 확보조치 기준 제5조제6항)
- **작성자의 ITGC 실무 경험**(공식 기준이 아니며 회사·업종별로 달라짐):
  - 일반 시스템 약 5회
  - 개인정보처리시스템·금융 약 3~5회
  - 잠금 해제: 자동(약 10~30분 후) 또는 관리자 수동
- **어디까지 검증**:
  - 회사 정책 문서에 횟수 명시 + 시스템 설정값 일치 검증
  - 감사 범위 내 시스템별 설정 적용범위를 확인하고 대표 사례 1건을 재수행하며 설정 변경 통제에 의존
  - 잠금 해제 절차 워크스루(셀프서비스 또는 관리자 승인)
- **결함 판단 기준은 통제 목적의 달성 여부다**:
  - 실패횟수 제한 설정 자체가 없음 (무제한) → **결함**. 통제 미작동
  - 정책은 5회이나 시스템은 무제한 → **결함**. 통제 미작동
  - 정책은 4회이나 시스템은 5회 또는 그 반대 → **정책과 설정의 불일치 사실을 기록**하고 원인·영향을 평가
  - 숫자 차이만으로 등급을 기계적으로 정하지 않으며, 정책과 다른 설정을 곧바로 적정하다고 단정하지 않음
  - 실제 운영 기준을 승인받아 정책에 반영하거나 시스템 설정을 정책에 맞게 보정

### Q3. 세션 타임아웃 — 몇 분이 표준?
A. **KISA와 현행 고시는 구체적인 시간을 정하지 않는다. 회사 위험평가·정책과 시스템 설정의 정합성을 본다.**
- 타임아웃 설정이 없거나 정책과 실제 설정이 다르면 통제 목적과 영향을 평가한다.
- 특정 시간이 길거나 짧은지는 회사 위험평가 결과를 기준으로 판단한다.

### Q4. SSO 적용 시 ITGC 검증 어디까지?
A. **작성자의 한국 비금융 ITGC 경험상 SSO 적용범위와 IdP의 MFA 정책을 주로 확인한다. 단계별 추가 인증이나 재인증은 보안 또는 ISMS-P 인증심사에서 다루는 경우가 많다.**
- 검증: SSO 적용 시스템 목록, IdP(Azure AD·Okta 등)의 MFA 정책, SaaS 로컬 계정의 SSO 우회 차단(→ 2.5.2 Q4)
- 중요 시스템 재인증은 ISMS-P 인증심사나 강화된 SOX 방법론에서 추가로 다룰 수 있다.
- SSO 인증 검증은 IdP 설정 적용범위 확인 + 대표 1건 재수행 + ITGC 일반통제 의존

### Q5. SMS OTP 결함인가?
A. **SMS OTP의 기술적 적정성은 일반 ITGC보다 보안정책과 위험평가에서 판단한다.**
- 안전성 확보조치 기준 제6조제2항은 일회용 비밀번호를 안전한 인증수단의 예로 든다. SMS 전달 방식의 구체적 적정성은 위험평가와 보안정책에서 별도 판단
- 인증수단 선택의 적절성 평가는 보안 진단 영역. ITGC는 회사가 정책 수립 + 일관 적용했는지만 본다
- 우회 가능 설정(예: "OTP 안 받음" 옵션)은 통제 무력화 → 결함

### Q6. 로그인 실패 메시지 "비밀번호가 틀렸습니다" — 결함?
A. **KISA 결함사례 2번에 명시되어 있지만 ITGC 실무에서는 거의 안 본다. ISMS-P 인증심사에서 다루는 영역이다.**
- ITGC가 본다면 외부 접속 가능 시스템(web 로그인)에 한정. 내부망 전용 시스템은 영향 ↓
- 단독 결함 등급 ↓. 실패횟수 제한 부재와 묶이면 결함 등급 ↑ (KISA 결함사례 2번 패턴)

### Q7. 2.5.3 영역, 한국 비금융 ITGC 실무에서 이거 다 봐야 함?
A. **모든 항목을 보지는 않는다. 보통 §3-A의 1~3번(비밀번호 정책·실패횟수·세션 타임아웃)과 외부 접속 인증수단(법적 의무) 정도만 본다. 1~3번은 한 번에 확인한다.**
- **한 번에 검증 가능**:
  - 시스템 설정 한 화면 (예: AD GPO·Linux PAM·DB 사용자 정책·web 인증 설정)에 비밀번호 정책·실패횟수·세션 타임아웃이 다 같이 나옴
  - 한 번의 설정 화면에서 1~3번을 함께 확인할 수 있더라도 시스템별 적용범위 확인 + 대표 1건 재수행 + ITGC 일반통제(설정 변경 통제) 의존
  - 시스템마다 분리된 화면일 수도 있지만 검증 절차는 같음 (캡처 → 회사 정책과 대조)
- **나머지 항목들의 위치**:
  - 동시 접속·로그인 실패 메시지·SSO 강화 인증 → ISMS-P 인증 받는 회사만 별도 검증
  - IP 기반 접근 제한·SIEM·UEBA·불법 로그인 경고 → **보안 영역**. ITGC가 아니라 보안조직(SOC)·보안 진단이 다룸
- **왜 갭이 있는가**:
  - 회계감사 ITGC는 재무제표 신뢰성에 영향을 미치는 IT 통제를 중심으로 한다.
  - 공격 탐지·대응 같은 보안 통제는 정보보호 영역에서 다루는 경우가 많다.
  - ISMS-P는 두 영역을 함께 요구하므로 ITGC 절차만으로 모든 기준을 충족할 수는 없다.
