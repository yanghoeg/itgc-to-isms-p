# 2.6.4 데이터베이스 접근

> **기준 판본**: [KISA ISMS-P 인증기준 안내서(2023.11.23)](https://www.isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do).
> **관련 법령**: 2026-07-26 기준.
> **내용 구분**: §1은 KISA 안내서 및 법령의 요약, §3~§4은 작성자의 실무 경험에 기반한다.

## 1. ISMS-P 기준 요약

### 인증기준
데이터베이스에 저장·관리되는 정보를 식별하고, 정보의 중요도와 응용프로그램·사용자 유형에 따른 접근통제 정책을 수립·이행하여야 한다.

### 주요 확인사항 (KISA 안내서)
1. 데이터베이스의 테이블 목록 등 저장·관리되는 정보를 식별하고 있는가?
2. 데이터베이스 정보에 접근해야 하는 응용프로그램·정보시스템·사용자를 명확히 식별하고 접근통제 정책에 따라 통제하고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무)
- 개인정보의 안전성 확보조치 기준 제5조 (접근권한의 관리), 제6조 (접근통제)

### 핵심 통제 (KISA 안내서)
- 테이블·컬럼과 저장 정보, 개인정보 위치·건수·암호화 여부의 식별 및 현행화
- 응용프로그램·서버·사용자별 데이터베이스 접근통제
- DBA·일반 사용자·응용프로그램 계정의 분리
- 중요 테이블·컬럼과 명령어에 대한 최소권한 적용
- 허용 IP·포트·응용프로그램 제한과 접근제어 우회 경로 차단

### 결함사례 (KISA 안내서)
- **사례 1**: 대량의 개인정보를 처리하는 데이터베이스와 인터넷 공개 웹 응용프로그램을 동일 서버에서 운영함
- **사례 2**: 개발자·운영자가 응용프로그램 계정을 공유하여 운영 데이터베이스에 접속함
- **사례 3**: 접근권한을 오브젝트별로 제한하지 않고 운영자에게 일괄 부여함
- **사례 4**: 접근 허용 IP 제한이 미흡하여 데이터베이스 접근제어 솔루션을 우회할 수 있음
- **사례 5**: 개인정보 테이블 현황을 파악하지 않아 임시 테이블에 불필요한 개인정보가 남아 있음

## 3. IT감사에서는 이렇게

### 3-A. 한국 비금융 ITGC 실무 적용

**2.6.4는 ITGC APD에서 독립 검증 절차가 있는 영역이다.** 2.6.2/2.6.3이 "다른 인증기준 커버"였다면, DB 직접접근은 애플리케이션 우회 데이터 변조 리스크가 있어서 별도로 본다.

핵심 질문: **"누군가 앱을 거치지 않고 운영 DB를 직접 수정할 수 있는가? 있다면 그 경로에 통제가 있는가?"**

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 1. DB 직접접근 제한 | 감사 범위 내 DB별 직접접근 가능 계정·IP 식별 → DBA 외 직접접근 가능자 존재 여부 | DB 사용자 마스터 전수 | 전수 추출 후 예외 분석 |
| 2. DBA 계정 적정성 | DBA 계정(sa·sys·sysadmin 등) 보유자 목록 → 직무 적정성과 인원 과다 여부 | DBA 계정 전수 | 전수 |
| 3. 직접변경 건 승인 **(→ PC 2.9.1)** | 직접변경 로그에서 표본을 추출하여 변경관리 승인·티켓 확인. **2.6.4는 경로·권한을, 변경 건은 PC에서 검증** | 기간 내 직접 변경 로그 | PC 감사계획에 따른 표본 |
| 4. 서비스 계정 관리 | 비밀정보의 보관·접근·변경 방식과 소스코드·설정파일의 평문 저장 여부 확인 | 감사 범위 내 응용프로그램 연결 계정 | 설정 확인 |

**직접 변경과 변경관리(PC)의 교차점**:
- **변경할 수 있냐(권한)는 APD, 실제 변경한 것의 확인은 PC.**
- **APD (2.6.4)**: 모집단 = **권한을 가진 계정 목록**(DB 사용자 마스터). 질문 = "직접 실행할 수 있는 권한·경로가 통제되는가"
- **PC (2.9.1)**: 모집단 = **실제 발생한 변경 로그**. 질문 = "변경내역이 승인·검토됐나". 일반적으로 데이터 수정은 Program Changes 영역이므로 **변경에 대한 테스트는 PC 통제**에서 수행
- 실무: DBA 직접 변경 로그에서 **표본 추출** → 변경관리 대장의 승인 건과 대조. 승인 없이 수행된 변경은 예외로 평가


### 3-B. ISMS-P 추가 요구사항 중 일반 ITGC 범위 밖

| ISMS-P 요구사항 | 절차 | 주된 담당 영역 |
|---|---|---|
| 개인정보 DB 암호화 | DB 암호화 적용 현황 점검 | **개인정보 영역** (3장) / 암호화 (2.7.1) |
| DB 접근 로그 장기 보존·정기 검토 | 로그 보존 기간·검토 절차 | **2.9.4** 로그 관리 (CO 영역) |

## 4. Q&A

### Q1. DB 직접접근 "원칙적 금지"인데, 실무에서 완전 차단 가능한가?

A. **완전 차단이 가능한 환경도 있지만, 운영상 직접접근이 필요한 경우가 있다.**
- 긴급 데이터 보정, 배치 오류 복구, 성능 튜닝 등으로 DBA의 직접 SQL 실행이 필요할 수 있음
- 통제 포인트는 "금지"가 아니라 **"승인 → 실행 → 기록 → 사후 검토"** 사이클
- ITGC 검증: 직접 변경 로그에서 표본 추출 → 승인 티켓 연계 확인. 승인 없는 건은 예외로 평가(변경 건 테스트는 PC 2.9.1)
- 직접접근 경로 자체를 차단한 회사 = jump server 경유 + DB 접근제어 솔루션(Chakra Max·DBSafer 등). 이 경우 솔루션 로그가 증적

### Q2. 서비스 계정(앱-DB 연결) 비밀번호, ITGC에서 어디까지 보나?

A. **비밀정보의 안전한 보관·접근·변경 방식과 평문 저장 여부를 확인한다.**
- 증적 = DB 연결 계정의 인증·비밀정보 관리 설정과 접근권한
- 소스코드·설정파일에 DB 비밀번호 평문 저장 여부 확인
- Vault·KMS 등 비밀번호 관리 솔루션 사용 여부 확인
- **금융권**은 설정값만이 아니라 **사람이 주기적으로 확인하는 수동 통제**(점검표·확인자 서명 등)가 추가로 들어감 — 설정 적정성 + 그 수동 통제의 수행 증적까지 본다
- 깊이 있는 코드 리뷰는 일반적으로 보안 진단·소스코드 점검 영역

### Q3. DB가 직접변경 로그를 안 남기면 모집단(표 3행)을 어떻게 만드나?

A. **DB 자체 로그 외에도 독립된 접근제어 솔루션 등 신뢰할 수 있는 원천을 검토한다.**
- **1차 모집단**: DB접근제어 솔루션(Chakra Max·DBSafer·Petra 등) 세션·쿼리 로그. 이게 있으면 표 3행을 솔루션 로그로 수행
- **솔루션도 없으면**: 직접변경 모집단을 만들 수 없다 → 탐지통제 부재. 이때는 **예방통제(접근 제한 등) 확인**
- 결함 판단 갈래:
  - 직접접근 경로가 막혀있음 → 탐지 로그 없어도 예방통제로 보완 (잔여리스크 낮음)
  - 직접접근이 열려 있는데 로그·솔루션이 모두 없음 → 변경의 식별·검토가 불가능한 통제 미비로 평가
- 감사인은 "로그를 남기는 기술을 사용해라"고 지정하지 않는다. ITGC는 통제 존재·운영을 평가하지 구현 수단을 강제하지 않는다
