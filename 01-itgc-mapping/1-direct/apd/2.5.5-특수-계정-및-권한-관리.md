# 2.5.5 특수 계정 및 권한 관리

> **기준 판본**: [KISA ISMS-P 인증기준 안내서(2023.11.23)](https://www.isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do).
> **관련 법령**: 2026-07-26 기준.
> **내용 구분**: §1은 KISA 안내서 및 법령의 요약, §3~§4은 작성자의 실무 경험에 기반한다.

## 1. ISMS-P 기준 요약

### 인증기준
정보시스템 관리, 개인정보 및 중요정보 관리 등 특수 목적을 위하여 사용하는 **계정 및 권한은 최소한으로 부여하고 별도로 식별하여 통제**하여야 한다.

### 주요 확인사항 (KISA 안내서)
1. 관리자 권한 등 특수권한은 최소한의 인원에게만 부여될 수 있도록 공식적인 권한 신청 및 승인 절차를 수립·이행하고 있는가?
2. 특수 목적을 위하여 부여한 계정 및 권한을 **식별하고 별도 목록으로 관리**하는 등 통제절차를 수립·이행하고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무)
- 개인정보의 안전성 확보조치 기준 제5조 (접근권한 관리)

### 특수권한 예시 (KISA 안내서)
- **관리자 권한**: Root, Administrator, admin, sys, system, sa 등 최상위 권한
- **배치프로그램 실행 권한**
- **보안시스템 관리자 권한**
- **계정 생성·접근권한 설정 권한**

### 핵심 통제 (KISA 안내서)
- 특수 계정·권한 발급·변경·해지 절차 수립 (일반 사용자보다 엄격)
- 임원 또는 보안책임자 승인
- 특수권한자 목록 작성·관리
- 예외처리 최소화, 모니터링 강화
- 외부자 특수권한은 필요할 때만 생성하고 업무 종료 후 즉시 삭제 또는 정지
- 특수권한자 현황을 정기적으로 검토하고 목록 현행화

### 결함사례 (KISA 안내서)
- **사례 1**: 관리자·특수권한 부여 승인 이력을 확인할 수 없거나 **승인 이력과 특수권한 내역이 불일치**
- **사례 2**: 특수권한 보유자 목록을 작성하지 않았거나 **보안시스템 관리자 등 일부 특수권한을 식별·관리하지 않음**
- **사례 3**: 유지보수용 특수계정 (분기 1회 방문)이 사용기간 제한없이 **상시 활성**
- **사례 4**: 정기 검토를 하지 않아 업무가 변경된 사용자가 **기존 특수권한을 계속 보유**

## 3. IT감사에서는 이렇게

### 3-A. 한국 비금융 ITGC 실무 적용

특수권한 통제는 ITGC APD의 핵심이며, 특수권한자가 일반 통제를 우회하거나 부정행위를 수행할 위험이 커서 회계감사에서 중요하게 본다.

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 1. 특수권한자 목록 | OS·DB·응용프로그램·네트워크별 root·admin·sa·sudoer 목록을 추출하여 회사 관리목록과 대조 | 전체 시스템 | 100% |
| 2. 부여 승인 절차 | 신청서·승인 이력 검증 (일반 신청보다 엄격한 승인선 적용 여부) | 특수권한 부여자 전체 | 샘플링 |
| 3. 외부자 특수권한 | 유지보수·컨설턴트 ID 목록, 부여·해지 이력, 업무 종료 후 회수 사례 확인 | 외부자 특수권한 전체 | 100% |
| 4. 정기 검토 (2.5.6과 연결) | 분기·반기 특수권한 검토 회의록·서명·결과 반영 이력 | 검토 사이클 | 검토 사이클 1~2건 |
| 5. 사용 모니터링 | 특수권한 사용 로그(sudo·관리자 접속·DB 직접접속) 보존과 이상 사용 검토 | 회사 정책상 보존기간의 로그 | 샘플링 + 워크스루 |
| 6. 배치 프로그램 권한 식별 | 배치 ID·서비스 계정 목록과 부여 사유 확인(2.5.2와 연결) | 배치 ID 전체 | 필요 시 100% |

### 3-B. ISMS-P 추가 요구사항 중 일반 ITGC 범위 밖

| ISMS-P 요구사항 | 확인 절차 | 주된 담당 영역 |
|---|---|---|
| 보안시스템 관리자 식별 | SIEM·방화벽·IPS 관리자 권한 목록 | **보안 영역** (SOC·정보보안팀) |
| 예외처리 최소화 정책 | 정책 + 사례 인터뷰 | ISMS-P 인증심사 |
| 임원·보안책임자 승인 강제 | 승인선 정책 검증 | ISMS-P 인증심사 (회사 위험평가에 따라 ITGC도 부분 검증) |

## 4. Q&A

### Q1. 특수권한 정의 어디까지? root만? sudo 사용자도?
A. **시스템별 최상위 권한 보유자 목록이 우선이다. sudo와 임시 권한은 실제 권한 범위와 사용 방식을 기준으로 분류한다.**
- **무조건 특수권한 (대상)**:
  - OS: root, 기본 Administrator
  - DB: sa, sys, system, root@localhost, oracle(DBA 권한)
  - 응용프로그램: admin, supervisor, sysadmin
  - 네트워크 장비: enable, privilege 15, admin
  - SaaS: Global Administrator, Owner
- **상황별 특수권한**:
  - sudoers 파일 등록자는 root 권한을 사용할 수 있으므로 **특수권한자로 분류**
  - 일회성 sudo 사용은 로그로 추적하며 상시 보유자 목록과 구분
  - wheel·sudo·dba 등 특수 그룹의 구성원도 특수권한자로 분류
- **어디까지 검증**:
  - OS·DB·응용프로그램별 특수권한자 목록의 추출 쿼리·명령을 명시(예: `getent group sudo`, `SELECT * FROM dba_role_privs`)
  - 회사 관리목록과 시스템 추출목록을 100% 대조
  - 차이가 있으면 원인과 영향범위를 확인하고 결함으로 평가
- **결함 판단**:
  - 시스템 추출목록과 회사 관리목록 불일치 → 결함
  - sudoer가 관리목록에서 누락됨 → 결함
  - 그룹 권한으로 부여된 특수권한이 관리목록에서 누락됨 → 결함

### Q2. 외부자 특수권한 (유지보수·컨설턴트) — 어디까지?
A. **KISA 결함사례 3번 영역. 부여 시점·종료 시점·즉시 삭제 검증이 핵심.**
- **검증 절차**:
  - 외부자 특수권한 부여 신청서 + 승인 이력 + 부여 시점 시스템 로그 대조
  - 업무 종료 시점 (계약 종료·작업 완료) + 권한 삭제·계정 정지 시점 시스템 로그 대조
  - 적시 회수 기준은 회사 정책을 우선하되 외부자 특수권한은 업무 종료 즉시 회수하는 것이 일반적(2.5.1 Q6 참조)
- **상시 활성 패턴 (전형적 결함)**:
  - 연 4회 방문하는 유지보수자 계정을 365일 활성 상태로 둠 → KISA 결함사례 3번
  - 컨설턴트 종료 후 계정 미정리 → 결함
  - 외주 PM 교체됐는데 이전 PM 계정 유지 → 결함
- **결함 판단**:
  - 부여 시 신청·승인 절차 없음 → 결함
  - 종료 후 적시에 회수하지 않음 → 영향평가 후 결함 수준 판단
  - 회수 정책 자체가 없음 → 전사 수준 통제 미비

### Q3. 특수권한자 정기 검토 주기 — KISA에 명시 있나?
A. **KISA는 구체적인 횟수를 정하지 않고 ‘정기적’ 검토를 요구한다. 회사 정책과 위험평가를 기준으로 2.5.6과 함께 본다.**
- KISA 안내서: "특수권한자 현황을 **정기적으로** 검토하여 목록 현행화"
- **작성자의 ITGC 실무 경험**(공식 기준이 아니며 회사·업종별로 달라짐):
  - 분기 1회: 많은 회사에서 사용하는 기본 주기
  - 반기 1회: 일부 비금융회사
  - 월 1회: 일부 금융회사·고위험 시스템
- **검증 절차** (2.5.6과 묶음):
  - 검토 회의록·결재 서명·검토 결과 반영 이력 (변경·삭제 사례)
  - 검토 → 시정 → 후속조치 과정을 워크스루
- **결함 판단**:
  - 정기 검토 자체를 수행하지 않음 → 결함(KISA 결함사례 4번)
  - 검토 후 시정하지 않아 업무가 변경된 사용자가 기존 권한을 계속 보유함 → 결함
  - 검토 주기가 회사 정책과 불일치 → 결함

### Q4. 임원·보안책임자 승인은 한국 비금융회사에도 항상 필요한가?
A. **KISA 안내서는 일반 사용자보다 엄격한 기준의 예로 임원 또는 보안책임자 승인을 제시한다. 실제 승인선은 회사 규모·업종·위험평가에 따라 달라질 수 있다.**
- **작성자의 ITGC 실무 경험**(공식 기준이 아니며 회사·업종별로 달라짐):
  - 대기업·금융회사: 보안책임자(CISO)·임원 승인선을 시스템에 강제하는 경우가 많음
  - 중견기업: 팀장·부서장 승인을 사용하는 경우가 많음
  - 중소기업: 구두·메신저 승인에 의존하면 승인 이력의 증명이 어려움
- **ITGC 시각**:
  - 임원 승인을 모든 회사의 절대 기준으로 단정하지 않음
  - **회사 정책 + 정책 일관 적용**이 결함 판단 기준 (2.5.4 Q1과 일관)
  - 회사가 팀장 승인 정책을 명시하고 위험평가 근거와 함께 일관되게 적용 → 적정성 평가 가능
  - 회사 정책상 "임원 승인"인데 실제 팀장 승인 → 정책-실제 불일치 결함
  - 회사 정책 자체 부재 → 전사 수준 통제 미비
- **ISMS-P 인증심사 시각**: 임원 승인 미적용도 회사 위험평가 결과에 따라 인정 가능. 다만 정책 문서 + 위험평가 결과 + 적용 일관성 다 갖춰야 함

### Q5. 한국 비금융 ITGC 실무, 2.5.5 어디까지 봐야 함?
A. **§3-A의 1~5번을 주로 확인한다. 특히 특수권한자 목록, 부여 승인, 외부자 회수는 ITGC APD의 핵심이다.**
- **무겁게 보는 이유**:
  - 특수권한자는 시스템 우회·로그 삭제·부정행위를 수행할 수 있는 위험이 큼
  - 회계감사 부정 위험과 직결 (회계감사기준서 240 영역 인접)
  - 작성자의 경험상 외부감사에서 결함이 자주 발견되는 영역
- **빈출 결함 패턴**:
  - 시스템 추출목록과 회사 관리목록 불일치(KISA 결함사례 1번)
  - 외부자 계정 상시 활성 (KISA 결함사례 3번)
  - 정기 검토를 수행하지 않거나 형식적으로 수행(KISA 결함사례 4번)
  - sudoer·그룹 권한 누락
- 보안시스템 관리자·배치 권한·예외처리 정책 등은 ISMS-P 인증심사나 보안 영역에서 추가 확인
