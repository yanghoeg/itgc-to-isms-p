# 2.5.2 사용자 식별

> **기준 판본**: [KISA ISMS-P 인증기준 안내서(2023.11.23)](https://www.isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do).
> **관련 법령**: 2026-07-26 기준.
> **내용 구분**: §1은 KISA 안내서와 법령을 요약했다. §3~§4에는 작성자의 실무 경험을 반영했다.

## 1. ISMS-P 기준 요약

### 인증기준
사용자마다 고유한 식별자를 부여하고 추측하기 쉬운 식별자의 사용을 제한해야 한다. 동일한 식별자를 불가피하게 공유하는 경우에는 타당성 검토, 책임자 승인, 책임추적성 확보 등 보완대책을 적용하여야 한다.

### 주요 확인사항 (KISA 안내서)
1. 사용자와 개인정보취급자마다 고유한 식별자를 부여하고 추측하기 쉬운 식별자의 사용을 제한하고 있는가?
2. 동일한 식별자를 불가피하게 공유하는 경우 사유와 타당성을 검토하고, 보완대책을 마련하여 책임자의 승인을 받고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무)
- 개인정보의 안전성 확보조치 기준 제5조 (접근권한의 관리)

### 핵심 통제 (KISA 안내서)
- 자연인 사용자에 대한 1인 1계정 원칙과 계정 공유 제한
- 운영계정에 대한 일반 사용자의 접근 제한
- 기본·시험 계정 제거 또는 추측하기 어려운 식별자와 비밀번호로 변경
- 공용계정 사용 시 사전 승인과 책임추적성 보완통제
- 임시 공유계정의 사용 종료 후 즉시 비밀번호 변경

### 결함사례 (KISA 안내서)
- **사례 1**: 기술적으로 변경할 수 있는 제조사 기본 관리자 계정을 변경하지 않고 사용함
- **사례 2**: 개발자가 타당성 검토나 책임자 승인 없이 개인정보처리시스템 계정을 공용으로 사용함
- **사례 3**: 외부 유지보수자가 별도 승인 없이 정보시스템 운영계정을 개인 계정처럼 사용함

## 3. IT감사에서는 이렇게

### 3-A. 한국 비금융 ITGC 실무 적용

사용자 식별은 로그 추적성의 전제다. ITGC에서는 1인 1ID 원칙과 기본·공용·서비스 계정의 별도 통제를 확인한다.

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 1. 1인 1ID | 사용자 마스터에서 동일 인물의 복수 ID 보유 여부 식별 | 전체 사용자 | 100% 규칙 기반 검토 |
| 2. 식별자 명명 규칙 | 사용자 ID 명명 패턴 검증 | 전체 사용자 | 100% 규칙 기반 검토 |
| 3. 추적성 | 로그·기록상 ID로 행위자를 식별할 수 있는지 워크스루 | 표본 거래·로그 | 샘플링 |
| 4. 공용 ID 통제 | 공용 ID 목록과 사용자 식별 가능성(개별 비밀번호·로그·세션 녹화) 검증 | 공용 ID 전체 | 100% |
| 5. 기본 ID 통제 | 기본 계정 목록, 비밀번호 변경, 사용 차단·제한 여부 검증 | 기본 계정 전체 | 100% |
| 6. 서비스 계정 분류 | 서비스 계정 목록, 비대화형 로그인 강제, 사용 시스템 명시 여부 검증 | 서비스 계정 전체 | 100% |

### 3-B. ISMS-P 추가 요구사항 중 일반 ITGC 범위 밖

| ISMS-P 요구사항 | 확인 절차 | 주된 담당 영역 |
|---|---|---|
| 비밀번호 공유 정황 책상 점검 | 포스트잇·메신저 비밀번호 공유 점검 | **보안 영역·내부감사** (2.5.4 Q4) |
| 보안 서약서·인식 교육 검증 | 비밀번호 공유 금지 정책 적용 사례 | ELC/인사 (2.2.3·2.2.4) |
| 메모리 덤프·세분 권한(SeDebugPrivilege 등) 검증 | 슈퍼유저 메모리 권한 침투 점검 | **보안 영역** (보안 진단·SOC) |
| 동시 다중 로그인 차단·이상행위 탐지 | UEBA·SIEM 룰 + 대응 절차 | **보안 영역** (SIEM·SOC) |

## 4. Q&A

### Q1. 동일 사번에 일반 ID + 관리자 ID 분리는 1인 1ID 위반인가?
A. **위반이 아니다. 일반 계정과 관리자 계정을 분리하는 것은 권장되는 방식이다.**
- **왜**: 일상 업무는 일반 ID로, 관리 작업은 관리자 ID로 분리하면 권한을 최소화할 수 있고 사용 로그도 명확해진다. PCI-DSS·ISO 27002에서도 권장한다.
- **어떻게**: 사용자 마스터에서 동일 인물 복수 ID 발견 시 → 권한 분리 목적인지(일반 vs 관리자), 단순 중복 발급인지 구분
- **결함 판단**:
  - 권한 분리 목적이고 명명 규칙이 일관되며 일반 ID에 관리자 권한이 없으면 적정
  - 단순 중복 발급 (회수 누락) → 결함

### Q2. 서비스 계정·시스템 계정도 1인 1ID 적용?
A. **자연인 사용자에게만 1인 1ID를 적용한다. 서비스 계정은 별도로 통제한다.**
- **왜**: 서비스 계정은 시스템 간 자동화·연계 목적으로 사용된다. 원칙적으로 사람이 사용하는 계정이 아니므로 ID 단위의 추적성 개념도 다르다.
- **어떻게**: 서비스 계정 목록을 별도로 관리하고 사용 시스템·인터페이스를 명시하며, 비대화형 로그인을 강제하고 별도의 비밀번호 정책을 적용
- **어디까지**:
  - 서비스 계정에 대화형 로그인(SSH/RDP) 차단 설정 검증
  - 사용 IP·시스템 화이트리스트 적용
  - 서비스 계정 비밀번호 vault 관리 (HashiCorp Vault·CyberArk 등)
- **결함 판단**:
  - 서비스 계정으로 사람이 대화형 접속한 로그 발견 → 결함
  - 서비스 계정 목록을 관리하지 않음 → 결함
  - 서비스 계정 비밀번호를 소스코드에 하드코딩함 → 중대한 결함 가능

### Q3. 기본 계정(root·Administrator·sa)을 삭제해도 되나?
A. **시스템 특성상 삭제할 수 없다면 비활성화·이름 변경·강력한 비밀번호·접근 제한으로 통제한다.**
- **왜**: 기본 계정이 부팅·복구·긴급 상황에 필요할 수 있으므로, 무조건 삭제하기보다 사용 제한과 로그 관리가 적절할 수 있다.
- **어떻게**:
  - 비밀번호 정기 변경 + 길이·복잡도 강화 + vault 보관
  - 일반 로그인 차단 (콘솔에서만 허용하거나 jump server를 경유하도록 제한)
  - 사용 시 사유·승인·로그 기록
  - Windows Administrator 계정 이름 변경(예: `Local-Admin-XYZ`)
- **결함 판단**:
  - 기본 비밀번호를 그대로 사용(admin/admin, sa/공백 등) → 결함
  - 사용 로그가 없음 → 결함
  - 평소 일반 로그인으로 사용 (별도 사유 없이) → 결함

### Q4. SaaS·SSO 환경에서 1인 1ID 어떻게 보나?
A. **IdP(Identity Provider) 기준으로 1인 1ID를 확인하고 SaaS 측 Provisioning을 검증한다.**
- **왜**: SSO 환경에서는 IdP가 기준 계정 시스템이다. 각 SaaS 계정은 보통 IdP에서 프로비저닝되므로 IdP 단계에서 1인 1ID를 검증한다.
- **어떻게**:
  - IdP (Azure AD/Okta/Google Workspace) 사용자 마스터에서 동일 인물 복수 계정 식별
  - SaaS 측에 IdP에서 SCIM/JIT로 프로비저닝된 계정 외 수동 생성 계정이 있는지 식별
  - SSO를 우회할 수 있는 SaaS 로컬 계정 존재 여부 검증
- **결함 판단**:
  - SaaS에 IdP 외 로컬 계정이 존재하여 SSO를 우회할 수 있음 → 결함
  - IdP에 동일 인물 복수 계정 → 결함
  - 퇴직자를 IdP에서 비활성화했는데도 SaaS 로컬 계정으로 접속할 수 있음 → 결함

### Q5. ID가 개인에게 소속됨을 어떻게 확신? ID·비번 남이 쓸 수도 있는데?
A. **ID만으로 본인 사용이 보장되지는 않는다. 식별은 추적성의 문제이고, 본인 인증은 여러 통제가 함께 보장한다.**
- **왜**: 사용자 식별(2.5.2)은 ID를 기준으로 행위를 추적하게 하는 통제다. 실제 사용자가 본인인지 확인하려면 사용자 인증(2.5.3), 비밀번호 통제, MFA, 인적 보안, 정책 준수가 함께 작동해야 한다.
- **본인 사용 보장 통제 (다층)**:
  - **2.5.3 사용자 인증** — 비밀번호·MFA·생체 (본인만 아는/가진/인 것)
  - **2.5.4 비밀번호 관리** — 복잡도·주기·공유 금지
  - **2.2.3 보안 서약** — 비밀번호 공유 금지 명시 (위반 시 인사 조치 근거)
  - **2.2.4 인식제고 교육** — 비밀번호 공유의 보안 위험
  - **2.2.6 보안 위반 시 조치** — 위반 발견 시 인사 조치 절차
  - **화면 잠금 정책** (자리 비움 시) — 무인 ID 사용 차단
  - **동시 다중 로그인 차단** 또는 모니터링 — 한 ID 동시 사용 탐지
- **ITGC 검증 포인트**:
  - 비밀번호 공유 금지 정책과 보안 서약서 작성(전사 수준)
  - MFA 적용 여부 (특히 외부 접속·특수권한)
  - 비밀번호 정기 변경 + 복잡도 강제 (시스템 설정)
  - 화면 잠금 정책 (자동 잠금 시간) + GPO/AD 강제 적용
  - 동시 다중 로그인 차단 설정 또는 로그 모니터링
  - 위반 시 조치 절차 + 적용 사례 (인사 기록)
- **결함 판단**:
  - 비밀번호 공유 정황 발견(메신저·포스트잇·인터뷰 진술) → 결함
  - MFA 미적용 (필수 영역인데) → 결함
  - 동시 다중 로그인을 제한하지 않고 로그 모니터링도 하지 않음 → 결함
  - 화면 잠금 정책이 없거나 사용자가 임의로 해제할 수 있음 → 결함
  - 보안 서약서를 작성하지 않음 → 전사 수준 통제 미비 가능
- **현실 한계**: 비밀번호 공유는 ITGC로 100% 탐지할 수 없다. 정책과 교육, 여러 겹의 기술통제를 적용하고 의심 정황이 있으면 추가로 조사해야 한다. PKI 인증서와 본인 생체 MFA 결합은 본인확인 수준을 높이지만 100% 보장을 의미하지 않는다. **ITGC 결함 보고에서는 "비밀번호 공유 가능성"을 본질적 한계로 보고, 필요한 통제 계층 중 무엇이 빠졌는지를 평가한다.**
