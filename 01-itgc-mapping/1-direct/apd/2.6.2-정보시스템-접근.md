# 2.6.2 정보시스템 접근

## 1. ISMS 원본

### 인증기준
서버, 네트워크장비, 보안장비 등 정보시스템에 대한 접근은 사용자 인증, 접근권한 등을 고려하여 **안전하게 관리**하여야 한다.

### 주요 확인사항 (KISA 안내서)
1. 서버, 네트워크장비, 보안장비 등 정보시스템에 대한 접근을 통제하기 위한 **운영절차를 수립·이행**하고 있는가?
2. 서버에 대한 접근은 **인가된 사용자만** 가능하도록 통제하고 있는가? (원격접근 시 안전한 접근수단 적용)
3. 정보시스템에 접근할 수 있는 **IP, 포트 등을 제한**하고 불필요한 서비스를 비활성화하고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무)
- 개인정보의 안전성 확보조치 기준 제6조 (접근통제)

### 핵심 통제 (KISA 안내서)
- 서버 OS·DB·App 접근 시 인가된 사용자만 접근
- 접근 가능 IP·포트 제한 (화이트리스트)
- 불필요 서비스·포트 비활성화
- 원격 접근 시 안전한 접속수단 (VPN·전용회선·jump server)
- 운영 서버 vs 개발·테스트 서버 분리 접근
- 콘솔(물리) 접근 통제

### 결함사례 (KISA 안내서)
- **사례 1**: 서버 접근 시 별도 인증절차 X — 내부망 접속만으로 서버에 직접 SSH/RDP 가능
- **사례 2**: 서버 접근 IP 제한 X — 내부망 모든 PC에서 운영 서버 접근 허용
- **사례 3**: 불필요 서비스·포트 다수 활성 (Telnet·FTP·미사용 포트) 방치
- **사례 4**: 운영 서버 접근과 개발 서버 접근이 동일 경로·동일 권한으로 구분 X

## 2. ITGC 매핑

| 항목 | 값 |
|---|---|
| 분류 | 직접 (1-direct) |
| ITGC 영역 | APD (Access to Programs and Data) |
| 부영역 | — |
| 보조 영역 | CO/operations (서버 접속 로그 → 2.9.4), 2.6.1 (네트워크 분리와 연결) |

## 3. IT감사에서는 이렇게

### 3-A. 한국 비금융 ITGC 실무 표준 (실제 검증 범위)

2.6.2 = 서버·장비 논리적 접근 통제. ITGC APD에서 2.5.x(계정·권한)와 함께 양대 축. 2.5.x가 "누구에게 권한을 줬나"라면 2.6.2는 "그 권한으로 어떤 경로로 접근 가능한가"를 본다.

| ISMS 요구 | ITGC 테스트 절차 | 모집단 | 샘플 |
|---|---|---|---|
| 1. 서버 접근자 list | OS별 사용자 마스터 추출 + 인가자 list 대조 (2.5.1·2.5.5와 연계) | 전 서버 사용자 | 100% (rule-based) |
| 2. 접근 IP 제한 | 서버별 접근 허용 IP whitelist (방화벽 룰·호스트 방화벽·TCP Wrapper 등) | in-scope 서버 전체 | 100% (rule-based) |
| 3. 원격 접근 경로 | 외부 → 서버 접근 시 VPN·jump server 경유 강제 검증 (2.6.1과 연계) | 원격 접근 경로 전체 | 100% |
| 4. 운영·개발 분리 | 운영 서버와 개발·테스트 서버의 접근 경로·접근자 분리 | 운영·개발 서버 | walkthrough |
| 5. 접근 로그 | 서버 접속 로그 보존 + 이상 접근 검토 절차 (2.9.4와 연계) | 로그 보존 기간 | 샘플 + walkthrough |

### 3-B. ISMS-P가 추가로 요구하지만 ITGC 실무 범위 밖

| ISMS 요구 | 절차 | 어디 영역 |
|---|---|---|
| 불필요 서비스·포트 비활성화 | OS·장비 hardening 점검 (Telnet·FTP·미사용 포트) | **보안 영역** (보안 진단·취약점 점검) |
| 콘솔(물리) 접근 통제 | 서버룸 출입 + 콘솔 잠금장치 | **물리 보안** (2.4.x) |
| 보안장비(IPS·IDS·WAF) 접근 통제 | 보안장비 관리자 접근 제한 | **보안 영역** (SOC·정보보안팀) |
| 네트워크장비 접근 통제 | 스위치·라우터 관리 인터페이스 접근 | **보안 영역** (네트워크 운영팀) |

**핵심 갭**: KISA 안내서는 "서버·네트워크장비·보안장비" 셋 다 나열하지만, 한국 비금융 ITGC 실무에서는 **재무제표 영향 서버(in-scope)만** 본다. 네트워크·보안장비 접근 통제는 보안팀 영역. ISMS-P 인증 받으려는 회사는 ITGC에 추가로 보안 진단 별도 발주.

## 4. Q&A

### Q1. "서버 접근" = SSH만? RDP·콘솔·API·DB 직접접근도?

A. **프로토콜 불문. 서버에 도달하는 모든 논리적 접근 경로가 대상. 단, DB 직접접근은 2.6.4에서 별도.**
- **포함**:
  - SSH (Linux/Unix)
  - RDP (Windows)
  - 웹 관리 콘솔 (vSphere·iLO·iDRAC·클라우드 콘솔)
  - API (REST·SSH key·service account 경유)
  - 파일 전송 (SCP·SFTP)
- **별도 인증기준**:
  - DB 직접접근 (SQL*Plus·SSMS·psql) → **2.6.4** 데이터베이스 접근
  - 콘솔(물리) 접근 → **2.4.x** 물리 보안
- **ITGC 시각**: 프로토콜이 뭐든 **인가된 사용자 + 인가된 경로(IP whitelist·jump server)**만 가능한지가 본질. 프로토콜 자체 보안 강도(SSH v1 vs v2, TLS 버전 등)는 보안 진단 영역

### Q2. Jump server(bastion host) 도입 = 무조건 OK? 우회 경로는?

A. **jump server 도입 ≠ 자동 OK. 우회 경로 차단까지 확인해야 통제 유효.**
- **jump server 유효성 검증** (ITGC에서 보는 것):
  - 서버 방화벽 룰: jump server IP 외 SSH/RDP 차단 확인 (§3-A 행 2)
  - jump server 자체 접근 통제: 인가자만 접근 (2.5.5 영역)
  - jump server 접속 로그 보존 (2.9.4 영역)
- **우회 경로 (빈출 패턴)**:
  - 방화벽 룰에 jump server 외 IP 허용 건 존재 (예외 처리 누적)
  - 서버 자체 방화벽(iptables·firewalld·Windows Firewall) 미설정 → 네트워크 방화벽만 의존
  - VPN 접속 후 jump server 거치지 않고 직접 접근 가능
  - 클라우드 Security Group에 0.0.0.0/0 허용 (개발 시 열어놓고 안 닫음)
- **ITGC 검증 깊이**:
  - 방화벽 룰 dump에서 jump server IP 외 허용 건 식별 = **ITGC 표준** (§3-A 행 2)
  - 서버 자체 방화벽까지 검증 = 회사 규모·위험 수준에 따라 (대형은 봄, 중소는 안 봄)
  - 침투 테스트로 우회 경로 직접 확인 = **보안 진단 영역. ITGC X** (2.5.1 Q2와 일관)
- **결함 판단**:
  - jump server 도입 + 방화벽 룰에 jump server 외 IP 허용 건 다수 → 결함
  - jump server 미도입 + 서버별 IP whitelist로 통제 → OK (jump server는 수단이지 의무 X)
  - 접근 통제 자체 X (모든 내부 IP에서 접근 가능) → 즉시 결함

### Q3. 클라우드 서버 (EC2·VM·GCE) — 어떻게 적용?

A. **on-prem과 통제 목표 동일. 수단이 다름 (Security Group·IAM·Session Manager 등).**
- **클라우드 환경 통제 매핑**:

| on-prem 통제 | 클라우드 대응 |
|---|---|
| 방화벽 IP whitelist | Security Group·NACL inbound rule |
| jump server | Bastion host EC2 / Azure Bastion / AWS SSM Session Manager |
| OS 사용자 list | IAM 역할 + SSH key 배포 / AD 조인 |
| VPN | AWS Client VPN / Azure VPN Gateway / GCP Cloud VPN |
| 접속 로그 | CloudTrail·VPC Flow Log·Azure Activity Log |

- **클라우드 특유 리스크**:
  - Security Group 0.0.0.0/0 inbound 22/3389 허용 (가장 빈출)
  - IAM 정책 과다 부여 (AdministratorAccess) → 콘솔에서 모든 서버 접근
  - SSH key pair 공유 (팀원 전원 동일 key)
  - Session Manager 사용 시 OS 사용자 list와 별개 경로 생김 → 양쪽 다 검증 필요
- **ITGC 시각**: 통제 목표 = on-prem과 동일 (인가자만·인가 경로만). 수단이 클라우드 native로 바뀔 뿐. Security Group 룰 dump = 방화벽 룰 dump와 동일 검증
- **결함 판단**:
  - 0.0.0.0/0 inbound SSH/RDP → 즉시 결함
  - SSH key 공유 + 개인 식별 X → 결함 (2.5.2 추적성 위반과 연결)
  - Session Manager 경유 접근 시 CloudTrail 로그만 남고 OS 로그 X → 로그 보존 검증 필요 (결함 여부는 정책과 대조)

### Q4. 개발·테스트 서버도 동일 수준으로 봐?

A. **동일 수준 X. 운영 서버만 in-scope. 단, 운영과 같은 네트워크 segment면 검증.**
- **원칙**: 회계감사 ITGC = 재무제표 영향 시스템(in-scope). 개발·테스트 서버는 통상 in-scope X
- **검증하는 경우**:
  - 개발 서버에 운영 데이터(개인정보·재무 데이터) 복사 → in-scope 편입 가능
  - 개발 서버와 운영 서버가 같은 네트워크 segment → lateral movement 위험 → 분리 검증 (2.6.1과 연계)
  - 개발 서버에서 운영 DB 직접 접속 경로 존재 → 결함
- **§3-A 행 4가 보는 것**: 운영·개발 분리가 되어 있는지 walkthrough. 개발 서버 자체 보안 깊이 검증은 X
- **결함 판단**:
  - 개발·운영 같은 segment + 접근 통제 동일 → 결함 (분리 미흡)
  - 개발 서버에 운영 데이터 무통제 복사 → 결함 (2.6.4·데이터 보호 영역과 연결)
  - 개발·운영 분리 + 개발 서버 자체 보안 미흡 → ITGC 결함 X (보안 진단 영역)

### Q5. 한국 비금융 ITGC 실무, 2.6.2 어디까지 봐야 함?

A. **§3-A 5개. 핵심 = 서버 접근자 list(행 1) + IP whitelist(행 2) + 원격 접근 경로(행 3). 2.5.x와 묶여서 APD 검증의 양대 축.**
- **2.5.x와의 관계**:
  - 2.5.1~2.5.6 = "누구에게 어떤 권한을" (계정·권한 라이프사이클)
  - 2.6.2 = "어떤 경로로 접근 가능한가" (접근 경로 통제)
  - 보통 한 세트로 검증. 서버 사용자 list 추출할 때 접근 IP whitelist도 같이 확인
- **보지 않는 영역**:
  - 불필요 서비스·포트 비활성화 → 보안 진단 (취약점 점검 보고서로 확인하되 ITGC가 직접 hardening 검증 X)
  - 콘솔(물리) 접근 → 물리 보안 (2.4.x)
  - 네트워크·보안장비 접근 → 보안팀 영역
- **빈출 결함 패턴**:
  - 방화벽 룰에 과다 허용 (내부망 전체 → 서버) — KISA 결함사례 2번
  - jump server 도입했지만 예외 IP 누적으로 우회 가능
  - 서버 OS 사용자 중 미인가자 (퇴직자·외부자 미회수와 묶임 — 2.5.1·2.5.5)
