# 2.9.1 변경관리

> **기준 판본**: [KISA ISMS-P 인증기준 안내서(2023.11.23)](https://www.isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do).
> **관련 법령**: 2026-07-26 기준.
> **내용 구분**: §1은 KISA 안내서와 법령을 요약했다. §3~§4에는 작성자의 실무 경험을 반영했다.

## 1. ISMS-P 기준 요약

### 인증기준
정보시스템 관련 자산의 모든 변경내역을 관리할 수 있도록 절차를 수립·이행하고 변경이 성능·보안에 미칠 영향을 사전에 분석해야 한다.

### 주요 확인사항 (KISA 안내서)
1. 하드웨어·운영체제·상용 소프트웨어 패키지 등 정보시스템 관련 자산의 변경 절차를 수립·이행하고 있는가?
2. 변경 수행 전 **성능·보안 영향을 분석**하고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무) — 간접

### 핵심 통제 (KISA 안내서)
- 변경 요청, 책임자 검토·승인, 변경 확인·검증
- 자산목록·운영 매뉴얼·구성도 등 관련 문서의 현행화
- 변경 이력 관리
- 변경 전 보안·성능·업무 영향 분석
- 변경 실패에 대비한 복구방안 마련

### 결함사례 (KISA 안내서)
- **사례 1**: 이중화 변경 후의 보안위험과 성능 평가에 관한 수행·승인 증거가 없음
- **사례 2**: 네트워크 변경 관련 검토·공지가 미흡하여 구성도와 접근통제 목록에 변경이 반영되지 않음
- **사례 3**: 변경관리시스템을 우회한 변경이 가능하고 해당 변경을 적절히 검토하지 않음

## 3. IT감사에서는 이렇게

### 3-A. 한국 비금융 ITGC 실무 적용

**2.9.1은 ITGC PC의 중심이 되는 변경관리 기준이다.** 다음 질문을 기준으로 검토한다. **"운영 시스템에 들어간 모든 변경이 승인·테스트·적절한 이관을 거쳤는가, 그리고 변경할 권한과 이관할 권한이 분리되어 있는가."**

통제는 **요청 → 승인 → 테스트 → 이관**의 4단계로 나뉜다. 핵심은 단계 간 직무분리(SoD), 즉 **개발자(변경 작성)와 이관자(운영 반영)의 분리**다.

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 1. 변경 승인 | 변경 모집단에서 표본 추출 → 변경요청·승인 증적 확인 | 기간 내 운영 반영 변경 전수 | 감사계획에 따른 표본 |
| 2. 테스트 | 표본 변경의 사용자 인수 테스트(UAT)·기타 테스트 결과 증적 확인 | 위 표본 | 감사계획에 따른 표본 |
| 3. 이관 직무분리 | 운영 이관 권한 보유자가 개발자와 분리됐는지 확인 | 이관 권한 보유 계정 | 전수 |
| 4. 긴급변경 | 긴급변경 목록에서 신속 승인 또는 불가피한 경우 사후 승인·정당성 증적 확인 | 긴급변경 전수 | 전수 또는 감사계획에 따른 표본 |
| 5. 모집단 완전성 | 변경관리 대장과 실제 운영 반영 기록(이관 로그·소스 타임스탬프) 대조 | 관련 배포·이관 기록 | 완전성 확인 |

PC의 핵심은 **변경 모집단의 완전성**이다. 변경관리 대장에 등록되지 않은 변경이 있으면 표본 추출 결과를 신뢰하기 어렵다. 운영 반영 기록(바이너리·소스 타임스탬프, 이관 로그)과 변경 대장을 역대조해 완전성을 확인하고 대장에 없는 이관은 비인가 변경 가능성이 있는 예외로 평가한다.

**2.6.4와의 연결**: DB **데이터 수정**도 PC 변경에 포함할 수 있다. 애플리케이션 변경과 DB 직접변경을 모집단에 포함한다. ([2.6.4 데이터베이스 접근](https://guide.propsol.co.kr/2.6.4) 교차점 참조 — "변경 권한은 APD, 실제 변경의 승인·검토는 PC")

**자동 배포(CI/CD·GitOps) 환경**: 도구 설정에 따라 파이프라인 승인 게이트·PR 검토·병합 이력이 변경 승인과 이관의 증적이 될 수 있다. 작성자 단독 병합·배포가 제한되는지, 독립된 검토자 승인이 강제되는지가 직무분리의 핵심이다.

### 3-B. ISMS-P 추가 요구사항 중 일반 ITGC 범위 밖

| ISMS-P 요구사항 | 절차 | 주된 담당 영역 |
|---|---|---|
| 변경 코드 품질·보안 취약점 | 정적분석·코드리뷰 | **보안 진단** (일반 ITGC 범위 밖인 경우가 많음) |
| 형상관리 도구 운영 상세 | 도구 설정·운영 | **운영 영역** |
| 변경에 따른 개인정보 영향 | 개인정보 영향평가(PIA) | **개인정보 영역** (3장) |

## 4. Q&A

### Q1. 변경 모집단 완전성, 어떻게 확보하나?

A. **변경관리 대장만 믿으면 안 된다.**
- 대장은 "신고된 변경"이지 "실제 일어난 변경"이 아니다
- 운영 이관 로그·소스 타임스탬프·배포 이력과 **역대조**하여 대장에 없는 이관 식별
- 모집단 완전성을 확인하지 않으면 통제를 우회한 변경이 표본에서 빠질 수 있음

### Q2. CI/CD·GitOps면 변경관리 증적이 뭔가?

A. **도구 설정과 절차에 따라 PR 승인·파이프라인 승인 게이트가 승인 증적이 될 수 있다.**
- PR 검토 승인과 병합·배포 이력이 내부 변경 절차의 각 단계에 어떻게 매핑되는지 확인
- 검증 포인트: 작성자 본인이 단독으로 병합·배포할 수 있는지, 검토자 승인이 브랜치 보호 규칙 등으로 강제되는지 확인
- 자동화된 환경에서도 SoD를 확인해야 하므로 승인 게이트의 권한 설정을 본다.

### Q3. 긴급변경(emergency change)은?

A. **신속한 사전 승인 절차를 우선 적용하고, 사전 승인이 불가능했던 경우에는 정해진 기한 내 사후 검토·승인이 필요하다.**
- 긴급변경 모집단에서 승인 방식·정당성·사후 검토 증적 확인
- 긴급변경 **비율이 과다**하면 정규 절차를 우회하는 신호가 되며, 그 자체가 통제 약화의 징후다.
- 정상 변경을 "긴급"으로 분류해 테스트·승인을 건너뛰는 패턴이 흔한 결함
