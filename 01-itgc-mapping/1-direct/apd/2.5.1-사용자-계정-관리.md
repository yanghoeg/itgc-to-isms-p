# 2.5.1 사용자 계정 관리

> **기준 판본**: [KISA ISMS-P 인증기준 안내서(2023.11.23)](https://www.isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do).
> **관련 법령**: 2026-07-26 기준.
> **내용 구분**: §1은 KISA 안내서와 법령을 요약했다. §3~§4에는 작성자의 실무 경험을 반영했다.

## 1. ISMS-P 기준 요약

### 인증기준
사용자 계정과 접근권한의 등록·변경·말소 절차를 수립·이행하고 업무상 필요한 최소 권한만 부여해야 한다. 계정과 권한을 부여할 때는 사용자가 본인의 보안책임도 명확히 이해하도록 해야 한다.

### 주요 확인사항 (KISA 안내서)
1. 사용자 계정과 접근권한의 등록·변경·삭제에 관한 공식 절차를 수립·이행하고 있는가?
2. 계정과 권한을 생성·등록·변경할 때 직무별 접근권한 분류체계에 따라 업무상 필요한 최소 권한만 부여하고 있는가?
3. 계정과 권한을 부여받은 사용자가 해당 계정에 따른 본인의 보안책임을 명확히 이해하도록 하고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무)
- 개인정보의 안전성 확보조치 기준 제5조 (접근권한의 관리)

### 핵심 통제 (KISA 안내서)
- 사용자별 고유 계정 발급 및 계정 공유(공유계정) 제한
- 계정·접근권한 발급과 변경 시 승인 및 적정성 검토
- 부서이동·퇴직 등의 인사이동 시 지체 없는 권한 변경 또는 말소
- 기본·시험(test) 계정 제거 또는 추측하기 어려운 계정으로 변경
- 계정·접근권한의 등록·변경·말소 이력 관리

### 결함사례 (KISA 안내서)
- **사례 1**: 공식 신청·승인 절차 없이 구두나 이메일로 계정·권한을 처리하여 승인·처리 이력을 확인할 수 없음
- **사례 2**: 업무 백업을 이유로 공식 절차 없이 미지정자에게 개인정보취급자 계정을 공유함
- **사례 3**: 업무에 필요하지 않은 과도한 권한을 부여하여 중요정보 또는 개인정보에 접근할 수 있음

## 3. IT감사에서는 이렇게

### 3-A. 한국 비금융 ITGC 실무 적용

2.5.1은 회계감사 ITGC의 APD 핵심 영역으로, 권한의 부여·사용·회수 전 과정을 다룬다. 작성자의 실무 경험상 외부감사에서 결함이 자주 발견되는 영역 중 하나다.

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 1. 등록·변경·삭제·잠금 절차 문서화 | 정책·절차 매뉴얼 입수 후 워크스루 수행 | 정책 1건 | 워크스루 1건 |
| 2. 신청 → 승인 → 처리 분리 (SoD) | 권한 매트릭스에서 신청·승인·처리 역할의 동시 보유자 식별 | 전체 권한 보유자 | 100% |
| 3. 신규 발급 적시성 | 신청서·승인 결재·시스템 발급 일자 정합 | 감사기간 신규 발급 계정 | 샘플링 |
| 4. 퇴직자 회수 적시성 | 인사부서 퇴직자 명단과 시스템 사용자 마스터를 대조하고 정책상 회수기한 준수 여부 확인 | 감사기간 퇴직자 전체 | 100% |
| 5. 휴면계정 점검 | 휴면계정 잠금 절차 증빙과 최근 로그인 일자 추출 | 전체 사용자 | 샘플링 |
| 6. 공용 계정 통제 | 공용 계정 목록과 개별 사용자 식별 가능성 검증 | 공용 계정 전체 | 100% |

### 3-B. ISMS-P 추가 요구사항 중 일반 ITGC 범위 밖

| ISMS-P 요구사항 | 확인 절차 | 주된 담당 영역 |
|---|---|---|
| 권한 변경 시 사용자 통지 | 변경 결재 → 본인 통지 절차 | ISMS-P 인증심사 |
| 직무변경 시 신규 권한 적정성 판단 | 신규 업무 권한 적합 여부 | **계정권한 모니터링** (2.5.6 검토 과정에서 확인) |
| 보안 서약·인식 교육과 연계 | 비밀번호 공유 금지 등 | ELC/인사 (2.2.3·2.2.4) |
| 외부자 계정 회수 검증 | 계약 종료 시 적시 회수 | 2.5.5 영역과 묶음 |

## 4. Q&A

### Q1. 휴면계정 N개월 기준이 회사마다 다른데, 무엇을 기준으로 판단하는지?
A. ISMS-P 안내서는 구체적인 개월 수를 정하지 않는다. ITGC에서는 **회사의 휴면계정 기준이 문서화되어 있고 일관되게 적용되는지**를 확인한다. 작성자의 실무 경험상 약 90일에서 180일을 사용하는 사례가 많지만, 이는 공식 기준이 아니며 회사·업종별로 달라진다.

### Q2. 공용 계정은 무조건 결함인가?
A. 무조건 결함은 아니다. **불가피한 사유, 사용자 추적성, 별도 비밀번호 관리**가 충족되는지 평가한다. 예를 들어 관리자 계정 하나를 여러 명이 비밀번호까지 공유하여 실제 행위자를 식별할 수 없다면 결함이다.

- **불가피한 공용계정 보완통제 예시**: 클라우드/DBA root 같이 기술적으로 공용이 불가피한 경우 → sudo 로그, 세션 추적 등의 보완통제를 확보
- **ITGC·ISMS-P 검증 깊이**: 정책·절차 + 로그 존재·점검까지가 일반적인 증적 범위. **우회 경로 검토(침투 테스트)는 별도 보안 진단 영역**이다.

### Q3. 메모리 덤프 막아야 하나? ITGC에서 어디까지 확인해야 하는지?

A. **일반적인 ITGC와 ISMS-P 인증심사에서는 통상 그 세부 권한까지 확인하지 않으며, 보안관제나 침투 테스트에서 다루는 경우가 많다.**

- **현실 (한국 시장)**:
  - **일반 비금융 ITGC**는 운영체제·데이터베이스의 슈퍼유저(root·Administrator·sa) 보유자 목록, 회수 절차, 사용 로그를 주로 확인한다. `SeDebugPrivilege` 같은 세부 권한은 통상 범위에 포함하지 않는다.
  - **금융권 ITGC**에서 사용하는 전자금융감독규정에서도 메모리 덤프에 관하여 별도로 명시하지는 않는다.
  - 작성자의 경험상 **ISMS-P 인증심사**도 2.5.5에서 root·admin·sa 등 일반적인 슈퍼유저를 중심으로 확인한다. KISA 안내서의 확인사항과 결함사례에도 메모리 덤프 권한은 별도로 명시되어 있지 않다.
  - 메모리 덤프 악용 여부는 보안관제나 침투 테스트에서 다루는 것이 일반적이다.

- **만약 클라이언트가 의뢰한다면**:
  - 별도 정보보호 컨설팅·보안 진단 계약으로 분리
  - 일반적인 ITGC·ISMS-P 절차에 포함하기에는 비용 대비 효과가 낮음

- **예외적으로 보는 경우**:
  - SOX 대상 미국 클라이언트 (일부 빅4 방법론에 SeDebugPrivilege 명시)
  - 강화된 보안 진단 의뢰가 별도로 들어왔을 때
  - 별도 보안 진단이 없는 한국 ITGC에서는 드묾

일반적인 ITGC에서는 슈퍼유저 보유자 목록, 회수 절차, 사용 로그까지 확인한다. 그보다 세분화된 메모리 권한은 보통 별도 보안 진단에서 다룬다.

### Q4. SSO(Single Sign-On)·IDM(Identity Management) 도입 클라이언트는 테스트 어떻게?

A. **감사 범위 내 각 시스템의 자동 회수 설정을 확인하고 대표 사례를 재수행하며, 관련 ITGC 일반통제에 의존한다. IDM이 없다는 사실만으로 결함은 아니다.**

- **자동통제(Automated Control) 테스트 원리**:
  - 동일 설정이 일관되게 적용되는 자동통제는 **해당 설정의 설계 확인 + 대표 1건 재수행**으로 동작을 검증
  - 자동통제에 의존하려면 관련 **ITGC 일반통제**가 효과적으로 운영되어야 한다.
    - PC: IDM 설정 변경 통제
    - APD: IDM 관리자 권한 통제
  - 관련 ITGC, 설정 적용범위, 대표 사례 재수행 결과가 모두 적정하면 같은 설정이 적용된 모집단을 신뢰할 근거로 삼을 수 있다.

- **IDM 도입 환경의 테스트 예시**:
  - 표본: 감사기간 인사부서 퇴직자 **1건**
  - 확인 절차:
    1. HR 퇴직 결재 시점 확인
    2. IDM 자동 회수 워크플로우 실행 로그
    3. 시스템 사용자 마스터에서 회수 결과
    4. 회수 일자 ≤ 퇴직 일자 + N일
  - ITGC 일반통제 별도 검증: IDM 설정 변경 통제, IDM 관리자 권한

- **IDM 없는 환경 (수기 통제)**:
  - 모집단: 감사기간 HR 퇴직자 전체
  - 샘플링 또는 인사부서 명단과 시스템 사용자 마스터의 100% 규칙 기반 대조
  - 수기 절차로도 적시 회수를 입증하면 적정하다.

- **결함 판단**:
  - 자동통제 대표 건에서 예외 발견 → 자동통제 의존을 중단하고 원인·영향범위를 확인한 뒤 모집단 확대 또는 대체절차 수행
  - ITGC 일반통제 결함(IDM 설정 변경 미통제, 관리자 권한 미관리) → 자동통제 신뢰성을 재평가한 후 모집단 확대 또는 대체절차 수행
  - 수기 통제에서 회수 지연·누락 → 결함
  - ITGC 일반통제와 자동통제 대표 사례가 모두 적정 → 자동통제에 의존 가능

- **인사부서 퇴직자 모집단 대조는 ISMS-P 안내서가 정한 절차가 아니다**:
  - ISMS-P 2.5.1은 절차 수립·이행과 인사이동 시 지체 없는 변경·말소를 요구하지만, 구체적인 감사 모집단이나 테스트 방식을 정하지 않는다.
  - 인사부서 퇴직자 명단과 시스템 사용자 마스터의 100% 대조는 회계감사 ITGC에서 사용하는 검증 절차다.
  - 따라서 같은 통제 목적이라도 회계감사 ITGC가 더 정량적인 검증 절차를 적용할 수 있다.

### Q5. 신청서가 없으면 무조건 결함인가?
A. **종이 신청서의 유무보다 승인·처리·추적 증적이 있는지를 본다.** 시스템상의 권한 변경 이력과 승인 결재가 신청서 역할을 대체할 수 있다. 다만 회사 정책이 특정 신청 절차를 의무화했다면 그 절차의 미준수 여부를 평가한다.

### Q6. 퇴직자 적시 회수 — '적시'의 기준은? 적시 회수 안 된 게 자동 결함?

A. **KISA 안내서는 절대 일수를 정하지 않는다. 회사 정책 준수 여부를 먼저 확인하고, 예외가 있으면 영향평가를 거쳐 결함 수준을 판단한다.**

#### 6-1. '적시'에 대한 회계법인 ITGC 실무 감각 (공식 표준이 아니며 회사·업종별로 달라질 수 있음)

| 산업·계정 유형 | 회계법인 ITGC 실무 감각 |
|---|---|
| 금융권·핀테크 일반 사용자 | 약 24시간 이내 |
| 금융권·핀테크 특수권한자 (admin/root) | **즉시** (퇴직 결재 시점) |
| 비금융 대기업 일반 사용자 | 약 1~3 영업일 |
| 비금융 중소 일반 사용자 | 약 7~14 영업일 |
| 외부자·계약직 (전 산업) | 계약 종료 **즉시** |
| 임원·주요직무자 | 일반보다 빨라야 (위험 가중) |

#### 6-2. KISA 안내서·결함사례 표현

KISA 안내서는 전보·퇴직 등 인사이동 시 접근권한을 **지체 없이** 변경하거나 말소하도록 설명하지만, 절대 일수나 월 단위 일괄 회수 사례, 인사시스템 자동 연계 의무를 별도로 제시하지는 않는다. 월 단위 일괄 회수는 지연 기간이 길어질 수 있으므로, 회사 정책과 실제 위험을 기준으로 ‘지체 없이’ 요건 충족 여부를 평가한다.

#### 6-3. 결함 여부는 자동으로 정해지지 않으며 영향 평가를 거침

회계감사 ITGC 결함 등급:
1. **통제 미비점 (Deficiency in Internal Control)** — 통제가 왜곡표시를 적시에 예방·발견·수정하도록 설계·운영되지 못한 상태
2. **유의적 미비점 (Significant Deficiency)** — 감사인의 전문가적 판단에 따라 지배기구가 주목할 만큼 중요한 통제 미비점 — 한국 회계감사기준서 265 정의 영역
3. **중요한 취약점 (Material Weakness)** — 중요한 왜곡표시가 적시에 예방 또는 발견되지 않을 합리적 가능성이 존재하는 미비점 — **PCAOB AS 2201 용어이며 한국 회계감사기준서 265의 직접 분류는 아님**

영향 평가 요소:
- **회수 지연 케이스 비율** (1/30 vs 10/30)
- **퇴직자 권한 수준** (일반 vs ERP 마스터 계정 vs DB admin)
- **시스템 위험도** (재무제표 핵심 영향 시스템 vs 비핵심)
- **지연 기간** (1일 vs 1개월+)
- **퇴직 후 실제 활동 발생 여부** (로그상 미접속 또는 실제 활동)
- **보완통제 작동** (모니터링·이상행위 탐지·MFA 잠금)

예시:
- 퇴직자 1명, 7일 지연, 일반 사용자, 퇴직 후 로그인 없음 → 통제 결함이나 영향은 상대적으로 작을 수 있음
- 퇴직자 10명 중 3명, 30일+ 지연, ERP 권한, 퇴직 후 로그인 발견 → **유의적 결함** 또는 **중요한 취약점**
- 외부자 1명, 1주일 지연, ERP 마스터 권한, 활동 없음 → 외부자·고권한 요소로 인해 유의적 미비점 가능

#### 6-4. ISMS-P 인증심사 시각

회계감사와 결함 분류 체계가 다르다. 개별 결함의 처리 결과는 인증기관의 심사 절차와 시정조치 결과에 따라 달라지므로 아래처럼 기계적으로 단정하지 않는다.
- 결함 발견 시 원인·영향범위 확인과 시정조치가 요구될 수 있음
- 대량·핵심 시스템·외부자 관련 결함은 영향도가 커질 수 있음
- 단일·단기 지연도 사실관계와 반복성, 실제 접근 여부를 함께 평가
