# 2.5.6 접근권한 검토

> **기준 판본**: [KISA ISMS-P 인증기준 안내서(2023.11.23)](https://www.isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do).
> **관련 법령**: 2026-07-26 기준.
> **내용 구분**: §1은 KISA 안내서와 법령을 요약했다. §3~§4에는 작성자의 실무 경험을 반영했다.

## 1. ISMS-P 기준 요약

### 인증기준
정보시스템과 개인정보 및 중요정보에 접근하는 **사용자 계정의 등록·이용·삭제 및 접근권한의 부여·변경·삭제 이력을 남기고 주기적으로 검토**하여 적정성을 점검해야 한다.

### 주요 확인사항 (KISA 안내서)
1. 사용자 계정 및 접근권한 **생성·등록·부여·이용·변경·말소 등의 이력**을 남기고 있는가?
2. 적정성 **검토 기준, 검토주체, 검토방법, 주기 등을 수립**하여 정기적 검토를 이행하고 있는가?
3. 검토 결과 **과다 부여, 절차 미준수, 오·남용** 등 문제 발견 시 **조치 절차**를 수립·이행하고 있는가?

### 관련 법규
- 개인정보 보호법 제29조 (안전조치의무)
- 개인정보의 안전성 확보조치 기준 제5조 (접근권한 관리)

### 계정·접근권한 이력 항목 (KISA 안내서, 책임추적성 확보)

| 구분 | 기록 항목 |
|---|---|
| 신청정보 | 신청자/대리신청자, 신청일시, 신청목적, 사용기간 |
| 승인정보 | 승인자, 승인 또는 거부 여부, 사유 및 일시 |
| 등록정보 | 등록자, 등록일, 등록방법 (결재시스템 연동·수작업 등록 등) |
| 권한정보 | 대상 시스템명, 권한명, 권한 내역 |

### 보관 기간
- **개인정보처리자: 접근권한 기록 최소 3년 보관** (안전성 확보조치 기준)
- **접속기록은 별도 통제**: [안전성 확보조치 기준 제8조](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&chrClsCd=010201&dashNo=&docCls=jo&joBrNo=00&joNo=0008&urlMode=admRulScJoRltInfoR)는 접속기록을 원칙적으로 1년, 일정 대상은 2년 이상 보관하도록 하고 점검 주기·방법·사후조치 절차를 내부 관리계획에 정하도록 한다. 현행 조문은 모든 처리자에게 월 1회라는 고정 주기를 두지 않는다. 이 통제는 2.9.4에서 다룬다.

### 검토 주기 (KISA 안내서)
- KISA 안내서 명시: **"최소 분기 1회 이상 권고"**
- ‘권고’ 표현이므로 법정 고정주기는 아니며, 회사 위험평가 결과에 따라 조정 가능
- **작성자의 ITGC 실무 경험**(공식 기준이 아니며 회사·업종별로 달라짐): 분기 1회가 흔하고, 일부 비금융회사는 반기, 일부 금융회사·고위험 시스템은 월 단위로 검토

### 적정성 검토 항목 (KISA 안내서)
- 공식적인 절차에 따른 접근권한 부여 여부
- 접근권한 분류체계의 **업무목적·보안정책 부합** 여부
- 접근권한 승인자의 적절성
- **직무변경 시 기존 권한 회수 + 신규 업무 권한 적절 부여** 여부
- **업무 목적 외 과도한 접근권한** 부여 여부
- 특수권한 부여·변경·발급 현황·적정성 (2.5.5와 연결)
- **협력업체 등 외부자 계정·권한 적정성**
- 접근권한 신청·승인 내역과 **실제 권한 부여 일치 여부**
- **장기 미접속자 계정 현황 + 삭제·잠금** 여부
- **휴직·퇴직 시 지체 없이 계정·권한 회수** 여부 (2.5.1과 연결)

### 조치 절차 (KISA 안내서)
- 소명요청·원인분석·보완대책·보고체계
- 권한 변경 내용을 사용자·관련자에게 통지
- 반복 시 근본 원인 분석·재발방지 대책

### 결함사례 (KISA 안내서)
- **사례 1**: 검토 방법·주기·보고체계·오남용 기준을 구체적으로 정의하지 않아 **정기 검토를 수행하지 않음**
- **사례 2**: 장기 미사용자 계정 잠금·삭제 정책이 있으나 **6개월 이상 미접속 계정이 활성 상태로 남아 있음**
- **사례 3**: 권한 과다 부여·오남용 의심사례를 발견하고도 **상세조사·내부보고 등 후속조치를 하지 않음**

## 3. IT감사에서는 이렇게

### 3-A. 한국 비금융 ITGC 실무 적용

권한의 부여(2.5.1·2.5.5)·사용·검토가 하나의 통제 사이클을 이룬다. 작성자의 실무에서는 **검토 정책, 취합 보고서, 검토 모집단 워크스루, 발견사항 후속조치, 이력 보관**을 중심으로 확인한다. 검토에 사용한 회사 제공 정보(IPE)의 완전성과 정확성은 위험과 감사계획에 맞는 절차로 별도 평가하며, 세부 권한의 업무 적정성 판단은 현업 검토자의 책임이다.

> 작성자의 경험상 2.5.6은 ISMS-P와 한국 비금융 ITGC 실무의 범위 차이가 큰 영역이다. 취합 보고서의 존재만 확인하지 말고, **검토 결과가 실제로 기재되었는지, 검토자가 해당 부서의 권한 적정성을 판단할 수 있는 위치인지**를 함께 확인해야 한다.

| ISMS-P 요구사항 | ITGC 테스트 절차 | 모집단 | 표본 |
|---|---|---|---|
| 1. 검토 정책 수립 | 검토 기준·주체·방법·주기·보고체계를 정의한 정책 문서 확인 | 정책 1건 | 워크스루 1건 |
| 2. 검토 취합 보고서 | 부서별 검토와 취합 보고서의 서명·검토 결과 기재 확인 | 1년 검토 사이클 | **분기 2건 / 반기 1~2건**(작성자의 통제 빈도 기반 실무 기준) |
| 3. 검토 모집단 신뢰성 | 검토에 사용한 목록의 출처와 추출방식을 워크스루하고, 위험에 따라 IPE 완전성·정확성 절차 수행 | 검토 목록 | 워크스루 1건 + 필요한 IPE 절차 |
| 4. 발견사항 후속조치 | 취합 보고서의 발견사항·후속조치 항목과 실제 기재 건의 조치 여부 확인. 장기간 모두 ‘이상 없음’이면 형식적 검토 가능성을 추가 확인 | 기재된 발견사항 | 전수 가능 |
| 5. 이력 보관 | 감사대상기간의 부여·변경·삭제 이력 보유 여부와 별도 법정 보관기간 준수 여부 확인 | 감사대상기간 이력 | 샘플링 + 기간 검증 |

> 휴직·퇴직자 권한 회수, 장기 미접속자 처리, 외부자 계정 회수의 실제 운영 테스트는 2.5.1·2.5.5에서 수행할 수 있다. 2.5.6에서는 이 항목들이 정기 검토에 포함되고 예외가 후속조치되는지도 확인한다.

### 3-B. ISMS-P 추가 요구사항 중 일반 ITGC 범위 밖

| ISMS-P 요구사항 | 확인 절차 | 주된 담당 영역 |
|---|---|---|
| 검토 결과 사용자 통지 | 권한 변경 시 본인 통지 절차 | ISMS-P 인증심사 |
| 권한 분류체계의 업무목적 부합 | 분류체계 자체 적정성 검증 | ISMS-P 인증심사 |
| 권한 오·남용 패턴 분석 | UEBA·이상 사용 분석 | **보안 영역** (SIEM·SOC) |

## 4. Q&A

### Q1. 검토 주기 — KISA 분기 1회 권고가 강제인가?
A. **KISA 안내서의 ‘최소 분기 1회 이상’은 권고 표현이다. 회사 위험평가와 정책에 따라 주기를 조정할 수 있다.**
- KISA 안내서 요지: 검토 절차를 수립하고 **최소 분기 1회 이상 검토를 권고**
- 반기·연 1회로 조정하려면 위험평가와 보완 근거가 필요하다.
- **작성자의 ITGC 실무 경험**(공식 기준이 아니며 회사·업종별로 달라짐):
  - 분기 1회: 많은 회사에서 사용하는 기본 주기
  - 반기 1회: 일부 비금융회사의 저위험 시스템
  - 월 1회: 일부 금융회사의 특수권한·고위험 시스템
- **결함 판단**:
  - 정기 검토를 수행하지 않음 → 결함(KISA 결함사례 1번)
  - 회사 정책은 분기이나 실제 검토를 수행하지 않음 → 결함
  - 회사 정책은 반기이고 위험평가 근거와 일관된 운영이 확인됨 → 적정성 평가 가능
  - 정책, 검토 수행, 결과 보고와 후속조치가 함께 작동해야 함

### Q2. 검토 주체 — IT팀? 보안팀? 현업 부서장?
A. **업무상 필요성을 판단할 수 있는 현업 책임자가 검토하고, IT팀·보안팀은 목록 제공·결과 취합·시정 반영을 지원하는 방식이 일반적이다.**
- **현업 부서장 검토 (표준)**:
  - 현업 책임자는 부서원의 업무와 필요한 권한을 판단할 수 있음
  - IT팀·보안팀만 검토하면 개별 권한의 업무상 필요성을 판단하기 어려울 수 있음
- **IT팀·보안팀 역할**:
  - 검토 대상 목록 추출·제공
  - 검토 결과 취합·보고
  - 시정 조치 시스템 반영
- **검증 절차**:
  - 검토 회의록·서명자 확인 (현업 부서장 서명이 있는지)
  - 검토 대상 목록이 현업이 판단할 수 있는 형태로 제공됐는지 (시스템명·권한명·내역 포함)
- **결함 판단**:
  - IT팀 단독 검토로 현업의 업무 적정성 판단 근거가 없음 → 결함 위험
  - 검토 목록이 SQL 역할명처럼 지나치게 기술적이어서 현업이 판단할 수 없음 → 결함
  - 현업 책임자의 검토와 시정조치까지 확인됨 → 적정

### Q3. 회사가 검토에서 발견한 건 100% 후속조치 추적이 ITGC 표준?
A. **모든 상황에서 100% 추적한다고 단정할 수는 없다. 다만 보고된 발견사항의 후속조치 여부는 통제 운영의 핵심 증거다.**
- **한국 비금융 현실**:
  - 회사 취합 보고서에 발견사항을 명시적으로 집계하지 않는 경우가 있음
  - 보통 "검토 결과 이상 없음" 한 줄로 종결
  - 발견사항이 없다고 보고된 경우에도 검토의 충실성과 근거를 확인할 필요가 있음
- **그럼 ITGC가 뭘 보나**:
  - 취합 보고서 양식에 **발견 건 기재 칸·후속조치 칸 존재** 여부 (정책 적정성)
  - 기재된 발견 건이 있다면 → 후속조치 확인 (모집단 작아서 전수 가능)
  - 1년 내내 발견사항이 전혀 없는 패턴은 **형식적 검토 가능성을 나타내는 신호**
- **표준 절차 (회사 측)**:
  - 권한 과다 발견 → 소명 요청 → 필요성이 입증되면 사유를 기록해 유지하고, 입증되지 않으면 회수
  - 회수 시 사용자·관련자 통지
- **현실 함정**:
  - "지금 다 쓰는 권한"이라 회수 못 함 → 검토가 형식적 (KISA 결함사례 3번)
  - 회수 시 업무 영향 큼 → 단계적 회수 (모니터링 강화 → 일부 회수 → 전면 회수)
- **결함 판단**:
  - 후속조치 항목 자체가 없음 → 정책·양식 미흡
  - 장기간 모든 결과가 ‘이상 없음’이고 검토 근거도 부족함 → 형식적 검토 가능성
  - 발견사항을 기재했으나 후속조치하지 않음 → 결함

### Q4. 장기 미접속자·휴직·퇴직자·외부자 회수는 2.5.6에서 안 봐?
A. **실제 회수의 적시성은 2.5.1·2.5.5에서 테스트할 수 있고, 2.5.6에서는 해당 항목이 정기 검토에 포함되어 예외를 식별·조치하는지 본다.**
- ITGC 조서에서 다음과 같이 **검증 위치를 구분**할 수 있다.
  - 휴직·퇴직자 권한 회수: 2.5.1(인사 변동과 시스템 계정 대조)
  - 장기 미접속자 처리: 2.5.1(회사 정책 기준 쿼리와 잠금·삭제 이력)
  - 외부자 계정·권한 회수: 2.5.5(외부자 목록과 종료 후 회수)
- 2.5.6에서는 위 항목들이 검토 정책과 취합 보고서에 포함되었는지 확인한다.
- **결함 위치**: 휴직자 권한 미회수 발견 시 결함은 2.5.1에 기재한다. 2.5.6에서는 "검토 사이클이 그걸 못 잡았는지"만 평가한다.

### Q5. 한국 비금융 ITGC 실무, 2.5.6 어디까지 봐야 함?
A. **§3-A의 5개 항목을 중심으로 확인하되, IPE의 완전성과 정확성은 위험과 감사계획에 맞게 별도 테스트한다.**
- **ITGC가 보는 깊이 (5개)**:
  - 검토 정책 존재(워크스루 1건)
  - 취합 보고서가 정책대로 작성됐는지 + 검토 결과란 실제 채워졌는지 (분기 사이클 2건 등)
  - 검토에 사용된 목록의 출처와 추출방식(워크스루 1건)
  - 후속조치 항목의 존재 여부와 기재된 발견사항의 조치 결과 확인. 장기간 발견사항이 없고 검토 근거도 부족하면 형식적 검토 가능성을 추가 확인
  - 부여·변경·삭제 이력이 감사대상기간 보존됐는지
- **역할 구분**:
  - IPE의 완전성과 정확성 검증 깊이 → 위험과 감사계획에 따라 결정
  - 개별 사용자에게 그 권한이 필요한지 1차 판단 → 업무를 아는 현업 검토자
  - 감사인은 현업 검토의 설계와 운영, 근거의 신뢰성을 평가
- **2.5.6에서 빠진 항목 (다른 인증기준에서 봄)**:
  - 휴직·퇴직자 권한 회수 → **2.5.1**
  - 장기 미접속자 처리 → **2.5.1**
  - 외부자 계정·권한 회수 → **2.5.1·2.5.5**
- **빈출 결함 패턴**:
  - 검토 정책은 있으나 정기 검토를 수행하지 않음(KISA 결함사례 1번)
  - 취합 보고서에 검토 결과를 기재하지 않거나 후속조치가 누락됨(KISA 결함사례 3번)
  - IT팀만 검토하고 현업의 업무 적정성 판단 근거가 없음

### Q6. 2.5.6 검토 결함 발견 시 다른 통제까지 도미노로 무너지나?
A. **하나의 결함이 다른 통제를 자동으로 무효화하는 것은 아니다. 통제 간 의존성과 결함의 원인·범위를 평가하여 필요한 영역을 추가 검증한다.**
- **ISMS-P 시각**:
  - KISA 안내서는 2.5.6 단일 결함이 인증 결과에 미치는 효과를 기계적으로 정하지 않는다.
  - 실제 처리 결과는 결함의 영향, 반복성, 시정조치와 인증기관의 심사 절차에 따라 달라진다.
- **ITGC 시각 (PCAOB AS 2201 결함 분류)**:
  - Deficiency / Significant deficiency / Material weakness 3단계
  - 2.5.6 결함의 등급은 관련 계정·권한 부여 통제, 영향 시스템, 보완통제와 함께 평가
- **다른 통제 영향**:
  - **부여 통제(2.5.1·2.5.5)**: 검토는 사후 발견통제이므로, 부여 통제의 설계·운영 결과를 재확인
  - **SoD 의존 ITAC**: 접근권한 검토 결함이 ITAC에 미치는 영향은 해당 ITAC가 사용자 권한과 관련 ITGC에 얼마나 의존하는지에 따라 평가
  - **재무제표 영향**: 검토·부여·특수권한 통제의 결함이 결합되면 APD 영역의 신뢰성과 부정위험 평가에 미치는 영향이 커질 수 있음
- **비금융 소규모 현실**:
  - 작성자의 경험상 비금융 중소형 감사에서는 ITAC에 의존하기보다 실증절차를 확대하는 경우도 많음
- **결함 처리 흐름**:
  - 검토 결함 발견 → 부여 통제(2.5.1) 워크스루 결과와 관련 IPE 신뢰성 재확인
  - 부여·검토 통제가 모두 취약함 → 결합 영향을 평가하고 실증절차 확대 여부 결정

### Q7. 결함 발견 시 재수행이 추출부터인가? 시간이 많이 드는데 다른 통제도 새로 해야 하나?
A. **재수행 여부와 범위는 통제 성격과 위험에 따라 정한다. 결함을 발견했다고 모든 통제를 자동으로 재수행하지는 않으며, 영향평가 후 관련 영역을 추가 검증한다.**
- **회계감사기준서 500의 감사절차 중 이 문서에서 주로 사용하는 4가지**:
  - 회계감사기준서 500에는 외부조회, 재계산, 분석적 절차 등도 포함된다. 아래는 ITGC 워크스루에서 자주 쓰는 절차다.
  - **검사(Inspection)**: 취합 보고서·승인 로그·신청서 등 회사 산출물 확인
  - **질문(Inquiry)**: 통제 담당자에게 절차를 확인하며, 일반적으로 다른 절차와 결합
  - **관찰(Observation)**: 권한 신청·승인 등 통제 수행을 실시간 확인
  - **재수행(Reperformance)**: 감사인이 통제의 일부 또는 전부를 독립적으로 수행
- **2.5.6 검토 통제는 검사와 질문을 중심으로 하되 필요하면 재수행을 결합**:
  - 검사: 취합 보고서, 검토자 서명, 후속조치 확인
  - 재수행: 감사인이 권한 목록을 추출하여 회사 검토목록과 대조
- **결함 발견 시**:
  - 검토 결함 발견 → 부여 통제(2.5.1)와 관련 IPE 결과 재확인
  - 부여 통제에서도 이상 발견 → 결합 영향을 평가하고 추가 실증절차 또는 재수행 결정
- **시간 비용 현실**:
  - 작성자의 경험상 ITGC 단일 통제 워크스루에는 보통 수 시간이 걸림
  - 권한 목록 추출·대조를 포함한 재수행은 며칠 단위로 늘어날 수 있음
  - 모든 통제를 재수행하면 ITGC 검증 일정 자체가 비현실적이 됨
  - 외부감사는 통제 성격과 위험에 맞춰 검사·질문·관찰·재수행을 조합
